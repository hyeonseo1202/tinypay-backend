# Payment concurrency control

동일 사용자의 결제 요청이 동시에 실행될 때 잔액과 월 예산을 같은 값으로 읽는 문제를
방지하기 위해 MySQL 행 단위 비관적 쓰기 락을 사용한다.

## 잠금 순서

결제 승인은 항상 다음 순서로 잠금을 획득한다.

1. `AiRequest` 행 잠금
2. `Wallet` 행 잠금
3. 월 사용액 및 잔액 확인
4. 블록체인 결제와 결제 기록 저장
5. 지갑 잔액 차감
6. 트랜잭션 커밋과 잠금 해제

동일한 요청에 서로 다른 멱등성 키가 사용되어도 `AiRequest` 잠금이 중복 실행을 막는다.
서로 다른 요청이 같은 지갑을 사용하면 `Wallet` 잠금이 요청을 순서대로 처리한다.
월 사용액 조회도 지갑 잠금을 획득한 뒤 실행하므로 같은 사용자의 동시 결제가 이전 결제의
커밋 결과를 반영한 상태에서 한도를 확인한다.

충전 역시 같은 지갑 잠금을 사용해 결제와 충전이 동시에 기존 잔액을 기준으로 계산하는
lost update 문제를 방지한다.

## 도메인 잔액 연산

잔액 변경은 임의 값으로 교체하지 않고 `withdraw`와 `deposit`으로 제한한다.
`withdraw`는 잔액보다 큰 금액과 0 이하의 금액을 거부하므로 락과 별개로 도메인 불변식을
한 번 더 보호한다.

## 트레이드오프

현재 구조는 블록체인 RPC 호출 중에도 지갑 잠금을 유지한다. 정합성은 단순하고 강하게
보장하지만 외부 호출이 느리면 같은 지갑의 다음 요청 대기 시간이 길어진다.
거래 상태 머신을 도입할 때 잔액 예약 단계를 별도 짧은 트랜잭션으로 분리하면 잠금 시간을
줄일 수 있다.
